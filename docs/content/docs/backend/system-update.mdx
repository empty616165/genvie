# 在线更新与安全回退

管理后台的“系统配置 → 系统更新”只负责管理员鉴权、展示状态和发起操作。真正的 Docker、数据库备份与服务切换由宿主机上的 `open-ai-canvas-host-updater` 执行，业务后端不挂载 Docker Socket。

```text
管理员浏览器 → Backend 管理 API → 带 Token 的 Unix Socket → Host Updater → Docker Compose
```

## 更新来源

在系统更新页面选择并保存来源，随后重新检查版本：

| 预设 | GitHub 版本与更新文件 | 容器镜像 |
| --- | --- | --- |
| 官方直连（默认） | GitHub API、Release、Raw | `ghcr.io` |
| 镜像加速 | GitHub 加速前缀（默认 `https://gh-proxy.org/`）加原始 HTTPS 地址 | 容器镜像源（默认 `ghcr.nju.edu.cn`） |

展开“分别设置 GitHub 与容器镜像来源”可使用混合配置。GitHub 来源覆盖 Release 列表、目标版本 Compose、Host Updater 二进制和 `SHA256SUMS`；容器来源覆盖 backend、web、yingce-agent，迁移服务复用 backend 镜像。

两个地址都由宿主机环境变量决定，页面显示的是**实际生效值**而不是写死的域名：

| 变量 | 作用 | 默认值 |
| --- | --- | --- |
| `CANVAS_UPDATER_GITHUB_PROXY` | `gh_proxy` 来源使用的加速前缀，必须为 HTTPS | `https://gh-proxy.org/` |
| `CANVAS_UPDATER_IMAGE_MIRROR` | `nju` 来源使用的容器镜像仓库主机名 | `ghcr.nju.edu.cn` |
| `CANVAS_UPDATER_IMAGE_PULL_TIMEOUT` | 单个镜像的拉取预算，超时后会回退 `ghcr.io` | `45m` |

公共加速域名会失效或被限流（例如 `gh-proxy.com` 已对整站返回 403；`gh-proxy.org` 的 GitHub API 与全球匿名请求共用同一份匿名配额，繁忙时约半数请求直接返回 403 `API rate limit exceeded`），镜像源也可能在传输大层时中断。任一公共地址不可用时，用上面两个变量指向自建代理或自建镜像源，然后 `systemctl restart open-ai-canvas-updater`。把某个第三方公共地址当作长期保证是不可靠的；能自己控制的出口才是稳定解。

版本列表、目标 Compose 和更新器资产都会按「所选来源 → 官方直连」的顺序尝试。直连使用本机出口与可选 `CANVAS_UPDATER_GITHUB_TOKEN`，配额独立，所以即使加速前缀被限流也能完成版本发现；错误信息会同时列出两条出口各自的失败原因。

**建议**：如果服务器能直连 GitHub（`api.github.com` 与 `github.com` 可达），保持默认「官方直连」比任何公共加速域名更稳定；只有当直连确实不通时才改用加速前缀，并优先指向自建代理。

来源配置保存在宿主机更新器的 `state.json`，独立于部署 `.env`，重启和应用回退不会重置选择。保存新来源会清除上次版本检查及来源检测结果。检查、检测、更新和回退互斥，更新任务记录并固定自己的来源快照。GitHub 出口在所选来源失败时会回退到官方直连，但不会改用其他第三方代理。容器镜像同理：所选镜像源拉不动某个镜像时回退到 `ghcr.io` 的同一 digest，不会跳到别的第三方镜像源；GitHub Token 只用于官方 API 直连，不发送给 GH-Proxy。

“测试连通性”在宿主机异步执行，页面关闭后仍会继续。检测会查询目标 Release、下载并校验 Compose 配置、验证当前 CPU 架构的更新器校验条目，并读取三个镜像的多架构清单，确认包含当前 `linux/amd64` 或 `linux/arm64`。每项单独显示失败详情，HTTP 403/429 提示拒绝或限流，404 提示版本不存在或镜像尚未同步。

检测不下载完整容器层，也不安装更新器，不能替代更新前的完整拉取与 SHA-256 校验。正式更新在全部准备成功后才停服；通过所选镜像源拉取后，实际 `仓库@sha256:...` 写入 `.env`，不会再因仓库名固定为 `ghcr.io` 而拒绝南大源摘要。回退恢复原 `.env` 和本地旧镜像，使用 `--pull never`；旧镜像被清理时会报错。

检测会先验证所选 GitHub 出口本身可用，再检查版本、Compose 和更新器校验清单，因此加速前缀整站不可用时会直接体现在「GitHub 出口与 Release 版本列表」一项，而不是伪装成版本或镜像问题。

镜像服务属于第三方公共服务，其可用性以目标服务器实测为准。SHA-256 与 digest 验证内容完整性，不能单独证明第三方源的发布者身份。

## 镜像拉取失败排查

先跑只读诊断，它不修改任何配置，只报告三类出口是否可用：

```bash
bash scripts/diagnose-update-egress.sh
# 验证候选加速前缀
GITHUB_PROXY=https://your-proxy.example.com/ bash scripts/diagnose-update-egress.sh
```

拉取阶段失败发生在停服之前，服务仍按原版本运行，日志会写明「更新已中止，尚未修改运行版本」。

### 镜像源大层停滞（自动回退）

更新器**逐镜像拉取并单独计时**（`CANVAS_UPDATER_IMAGE_PULL_TIMEOUT`，默认 45 分钟/镜像），不再让三个镜像共享 20 分钟。某个镜像在所选镜像源拉不动时，会自动改用 `ghcr.io` 拉取**同一 digest** 的内容，并在日志写出「改用 ghcr.io 同一 digest」。

这样做是安全的：各源的多架构 index digest 完全一致，同一 tag 对应同一份内容；回退后仍会校验本地仓库摘要。实测：公共镜像源在小层上可能比直连更快，但超大层（约 122 MB）会掉到 100~200 KB/s 甚至完全停滞，此时回退是唯一能完成更新的路径。

只有可恢复的传输类失败（层摘要不符、`failed precondition`、连接重置、超时）才回退；鉴权拒绝、404、架构不符属于确定性失败，会立即中止而不是换源重试。

诊断脚本的第 3 节会实测大层吞吐，直接告诉你会不会撞上超时：

```bash
bash scripts/diagnose-update-egress.sh
```

### `unexpected commit digest … failed precondition`

表示本地 content store 中已有的层内容与清单摘要不一致。常见成因是上一次拉取被中断或超时留下半截层，或 Docker 数据目录空间不足导致层写入被截断。更新器现在会删除本次目标标签的本地引用并自动重试一次，同时把报错翻译成可执行提示。

人工处理顺序：

```bash
cd /opt/open-ai-canvas
# 把 <目标版本> 换成要升级到的版本号（去掉 v），只删这三个目标标签；
# 不要用 prune -a：会删除可用于回退的旧版本镜像
docker image rm --force ghcr.nju.edu.cn/empty616165/genvie-canvas-web:<目标版本> || true
docker image rm --force ghcr.nju.edu.cn/empty616165/genvie-canvas-backend:<目标版本> || true
docker image rm --force ghcr.nju.edu.cn/empty616165/genvie-canvas-yingce-agent:<目标版本> || true
docker system prune -f
df -h /var/lib/docker
```

确认空间充足后重新检查版本并更新。更新前要求 Docker 数据目录至少 4 GiB 空闲；更新器会在拉取前自动检查，读不到 Docker 数据目录时跳过该预检而不是阻塞更新。

### 公共镜像源传输中断

部分镜像源能返回正确的清单和多架构 index digest，但在传输大层（例如 120 MB 的 Web 层）时会长时间停滞或截断。清单校验通过并不代表整包可下载。此时应把 `CANVAS_UPDATER_IMAGE_MIRROR` 换成自建镜像或直连 `ghcr.io`，而不是反复重试同一个源。

### Docker 守护进程出口

更新器读取 GitHub 和镜像清单走自己的进程，真正下载镜像层的是 Docker 守护进程。若服务器需要代理出网，两边都要配置，否则会出现「检测通过但拉取失败」：

```bash
# /etc/systemd/system/open-ai-canvas-updater.service.d/proxy.conf
# /etc/systemd/system/docker.service.d/proxy.conf
[Service]
Environment=HTTP_PROXY=http://<代理地址>:<端口>
Environment=HTTPS_PROXY=http://<代理地址>:<端口>
Environment=NO_PROXY=localhost,127.0.0.1,::1,postgres,redis,yingce-agent,backend
```

`registry-mirrors` 只对 Docker Hub 生效，不能把 `ghcr.io` 重定向到其它仓库。

## 安全更新顺序

1. 从 GitHub Releases 读取包含预览版在内的最高语义版本，并与 `.env` 中固定的 `CANVAS_IMAGE_TAG` 比较。`sha-*` 这类非正式镜像标签一律视为低于正式 Release，避免把 `vsha-5509b17` 字典序比较成比 `v1.5.0` 更新。
2. 下载目标版本的 `docker-compose.deploy.yml`，执行 `docker compose config --quiet`，检查部署文件、磁盘空间和当前版本。当前标签不是 `vX.Y.Z` 或 `vX.Y.Z.N` 时，健康检查只确认服务就绪，不要求构建号和镜像标签逐字相同。
3. 拉取目标 backend/web/yingce-agent 镜像并要求存在仓库 `sha256` 摘要；下载期间旧服务继续运行，准备失败在停服前中止。
4. 停止 web/backend/yingce-agent，等待旧服务退出；PostgreSQL 和 Redis 保持运行。
5. 创建停服后的 `backup-YYYYMMDD-HHMMSS.zip.partial`，包含 PostgreSQL custom-format dump、后端数据目录 tar 和元数据；写入完成后 `fsync`、原子改名，并复核 ZIP 结构和 SHA-256。保存旧 Compose 与部署环境后才进入迁移。
6. 用目标 backend 镜像独立执行 `migrate-schema up`。整批迁移在事务和 PostgreSQL advisory lock 内完成，迁移名称与 checksum 必须匹配。
7. 解析目标 backend/web 镜像的仓库 digest，原子更新 `CANVAS_IMAGE_TAG`、`CANVAS_BACKEND_IMAGE`、`CANVAS_WEB_IMAGE` 和 Compose 文件，启动目标版本；运行容器始终使用 `image@sha256:...`，不使用 `latest`。
8. 连续检查 `/api/health/ready` 的数据库、运行时、schema 和 build version，并经过稳定窗口后才标记成功。

更新状态写入 `/var/lib/open-ai-canvas-updater/state.json`。Backend 或浏览器在切换期间断线不会终止宿主机操作，恢复后可继续读取日志。

停止服务或最终备份失败且尚未开始迁移时，直接启动原容器并验证健康，不恢复旧数据库快照。原容器恢复失败会进入 `manual_intervention`。备份耗时计入停服窗口。

数据目录归档通过原 backend 镜像的一次性容器执行 `tar`，挂载原数据卷，不启动业务入口或依赖服务，不重新拉取镜像；不再依赖已停止容器上的 `exec`。

## 自动回退

停服后的迁移、启动或健康验证失败会触发自动回退：

1. 停止目标 web/backend；
2. 恢复更新前保存的 Compose 文件；
3. 恢复更新前保存的 `.env`，确保 backend/web 镜像仍绑定到原 digest；
4. 再次校验备份 ZIP 和 SHA-256；
5. 使用 `pg_restore --clean --if-exists` 恢复 PostgreSQL；
6. 启动旧服务并重新进行稳定窗口验证。

回退任一步失败时状态变为 `manual_intervention`，不伪造成功。管理后台仅在存在旧版本和已校验备份时开放人工回退按钮。

该备份覆盖旧服务停止前的写入。新版本启动后产生的业务写入不在此快照中，历史备份回退仍可能覆盖这些写入；需按恢复时的数据和 schema 状态另行确认。

## 安装与升级约束

GHCR 镜像部署必须把 `CANVAS_IMAGE_TAG` 固定到具体 Release，并把 `CANVAS_BACKEND_IMAGE`、`CANVAS_WEB_IMAGE` 固定到所选 GHCR 或南大源的 digest，不可使用 `latest` 或仅使用可变 tag。发布仓库是 `empty616165/genvie`，镜像包为 `ghcr.io/empty616165/genvie-canvas-{web,backend,yingce-agent}`。首次安装时显式指定 Release：

```bash
curl -fsSL https://raw.githubusercontent.com/empty616165/genvie/main/scripts/install-server-image.sh \
  | sudo env CANVAS_IMAGE_TAG=v1.8.7.5 bash
```

已有部署只安装更新器时，先确认 `.env` 已包含两个 `@sha256:...` 镜像引用，再执行：

```bash
cd /opt/open-ai-canvas
curl -fsSL https://raw.githubusercontent.com/empty616165/genvie/main/scripts/install-host-updater.sh | sudo bash
```

`raw.githubusercontent.com` 在部分网络被阻断时，脚本本身也可以从 Release 资产取得，并通过 `GITHUB_PROXY` 加速下游下载：

```bash
curl -fsSL https://gh-proxy.org/https://raw.githubusercontent.com/empty616165/genvie/main/scripts/install-host-updater.sh \
  | sudo env GITHUB_PROXY=https://gh-proxy.org/ REPOSITORY=empty616165/genvie bash
```

两个脚本内部都按「GitHub 加速前缀 → raw 直连 → Release 资产」的顺序下载 Compose、安装脚本和更新器二进制，任一路径成功即可继续；全部失败时才报错并列出各候选地址的失败原因。加速前缀只接受显式配置，不会自动选择第三方代理。

重装 `install-host-updater.sh` 会重写 `/etc/open-ai-canvas-updater.env`，其中 `CANVAS_UPDATER_REPOSITORY` 取自 `REPOSITORY`（默认 `empty616165/genvie`），因此它也是把旧安装机从改名前的仓库地址迁移过来的入口。

脚本会下载与当前 Release 匹配的 Linux amd64/arm64 二进制和 `SHA256SUMS`，生成随机 `CANVAS_UPDATER_TOKEN`，创建 systemd 服务、Socket 目录、状态目录和 `backups/`。Token 只保存在服务器 `.env` 与 root-only 更新器环境文件中。

## 镜像发布与质量门禁

`main` 推送、`v*` 标签和手动发布统一由 `.github/workflows/publish-images.yml` 编排。发布先调用可复用的 `quality.yml`；PR 仍直接运行质量检查。Go 测试、前端格式、类型、Lint、单测和 Chrome E2E 任一失败，都不能进入镜像构建和发布阶段。若仓库规则配置了必需检查，切换后应核对实际 check 名称，避免仍等待旧的独立 push 工作流。

构建和发布分为以下阶段：

1. 校验 `VERSION`；版本标签必须与文件一致，且存在对应 `CHANGELOG.md` 标题。构建时间取提交时间，同一 SHA 不因重跑而改变。
2. 后端分别在 `ubuntu-24.04`（AMD64）和 `ubuntu-24.04-arm`（ARM64）原生编译，保留 CGO 与三个服务/迁移二进制。支付插件在每个平台的镜像阶段重新打包并执行 smoke；PR 则独立执行双架构 smoke，不依赖发布。
3. 前端 Bun 构建阶段固定到 `BUILDPLATFORM`，静态资源只生成一次，再放入 AMD64/ARM64 nginx 镜像。Bun 与 `web/package.json`、质量检查保持 `1.3.9` 一致。
4. 先推送 `sha-<完整提交>-amd64/arm64` 后端镜像及 `sha-<完整提交>-multi` 前端镜像，以摘要 artifact 传递结果。两种后端架构和前端全部成功后，才从摘要合并发布 manifest，不用可变标签作为合并源。
5. 同一 SHA 的 main/tag 发布串行运行。tag 一轮先查同 SHA 的 main 一轮：已整体成功就跳过质量检查，直接推广镜像并创建 Release；没有成功的 main 一轮（例如先推 tag、main 检查失败、查询出错）时照常完整检查。发版应先推 main 再推 tag。只有明确的镜像不存在可以转入构建，鉴权、限流、网络和异常摘要必须报错。
6. 发布保留完整 SHA 和短 SHA 标签；只有版本 tag 推送写入具体版本标签。`main` 只有在仍是远端最新提交时才更新 `latest`，旧提交的慢任务不能覆盖新版本。正式部署由安装器和更新器解析并落盘 digest，不依赖 `latest`。

Go 测试分 5 个并行 Runner：`internal/app` 的顶层用例按名字排序后轮转分成 `app-1`…`app-4`，其余包为 `rest`（同时做 gofmt 检查）。`Backend checks` 汇总各分片结果，要求全部通过并核对依赖 PostgreSQL / Redis 的用例确实运行，检查名保持不变。Go 检查显式使用 `backend/go.sum` 作为缓存依赖键，汇总后上传 `go-test-timings`（JSONL），可按 `Test` / `Elapsed` 定位慢测试。Docker 的后端模块下载保留在普通镜像层，编译步骤可以直接读取；支付插件只按实际 import 下载依赖，不重复预取完整后端模块图。版本参数下移到编译入口。GHA 构建缓存按镜像和架构隔离，避免并行任务共用同一 scope。`go-build` cache mount 只用于同一个 builder 内的复用，当前没有额外的跨 Runner mount 导出方案；不能把它当作持久编译缓存。冷缓存首轮和缓存上传仍可能较慢，需要比较连续两轮的实际耗时。

这套发布流程依赖仓库可使用 GitHub 原生 ARM64 Runner、GHCR 写权限以及构建/下载 artifact 能力。首次上线应核对实际 Runner 排队情况、双架构 manifest、main/tag 同 SHA 复用和质量失败阻断；本地测试不能代替这些云端验收。工作流变更不迁移业务数据库，也不修改服务器 Compose 或数据卷。需要回退 CI 时只回退工作流和 Dockerfile 改动；已发布镜像不会自动撤回，线上版本回退仍按本文的备份与迁移约束执行。

## 运维检查

```bash
sudo systemctl status open-ai-canvas-updater
sudo journalctl -u open-ai-canvas-updater -n 200 --no-pager
sudo ls -lh /opt/open-ai-canvas/backups
sudo sha256sum /opt/open-ai-canvas/backups/*.zip
```

备份文件包含业务数据，应限制为 root 访问并纳入异机备份策略。数据卷本身不是备份。
